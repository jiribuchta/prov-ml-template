prov-ml-template

What you must do to get your dataset through the pipeline —
and how this differs from the current (monolithic) pipeline.

One sentence

Fill in one YAML file per dataset, then run one command per step (locally or as a k8s job) — every step is a provenance-tracked MLflow run.

  • Each step is its own module (pipeline/<step>.py) and its own config (configs/pipeline/<step>.yaml) — run any step alone.
  • Downstream steps find their upstream automatically (latest finished run of that step), or via a pinned runs:/... URI in the experiment config.
  • Data is used in place — files stay where they are on the cluster, nothing is copied or created.

What you must do — 1. setup (once)

# clone, enter, and create the environment
uv sync

# point the pipeline at your MLflow server + identify yourself
export MLFLOW_TRACKING_URI=...
export MLFLOW_USER=...

Register yourself (once, first ever run)

# identity fields live in configs/pipeline/create_user.yaml — edit them first
uv run python -m pipeline pipeline=create_user +experiment=mammaprint

One run in the User_Registry — links all your future runs to you.

What you must do — 2. one YAML per dataset

Copy the template to configs/experiment/<your-dataset>.yaml and fill in the marked fields — this is the only dataset-specific file, versioned in git:

metadata:
  experiment_name: Dataset Mammaprint
  description: dataset init

data_path: /mnt/data/MOU/breast/mammaprint

pipeline:
  source:  null        # or cohort.xlsx
  pattern: '.*\.mrxs$'  # or null
  path_column: null    # table mode only
  label_column: null    # table mode only
dataset:
  name: mammaprint
  version: 1.0.0
  mlflow_uris:          # pin to freeze
    split_dataset: null   # the chain
    embed_dataset: null

Every step then runs with +experiment=mammaprint — no more long CLI flag lists that nobody can find again.

Second dataset later? Copy the file again, change the values.

What you must do — 3. point at your data

register_dataset accepts three input shapes (first match wins — that's the whole configuration):

1. A cohort table already existed

The csv/xlsx that usually ships with the data:

source: cohort.xlsx
path_column: slide
label_column: label

Paths absolute or relative to data_path.

2. A regex new

Folder + "what to find" — manifest is built for you:

pattern: '.*\.mrxs$'

Classes from a named label group ('^(?P<label>\d+)/.*\.svs$') or from the parent folder. Recursive; skips manifest.csv and hidden files.

3. The folder itself any file type

One subfolder per class:

data_path/
├── class_0/s1.mrxs
└── class_1/s2.mrxs

Previously hardcoded to */*.csv — now any file type.

What you must do — 4. run the steps

Locally, in order

uv run python -m pipeline pipeline=register_dataset +experiment=mammaprint
uv run python -m pipeline pipeline=split_dataset     +experiment=mammaprint
uv run python -m pipeline pipeline=embed_dataset     +experiment=mammaprint
uv run python -m pipeline pipeline=learn             +experiment=mammaprint

Each run prints the provenance chain and a [hint] line showing how to pin it for downstream steps.

On the cluster — one job per step new

# once: uv sync --extra job, edit scripts/_submit.py
# (image + EXPERIMENT = "mammaprint")
uv run python scripts/register_dataset.py
uv run python scripts/split_dataset.py
uv run python scripts/embed_dataset.py
uv run python scripts/learn.py

# or the whole chain in one job:
uv run python scripts/submit_pipeline.py

Username comes from your kube config; each job runs the step with full provenance (job_* tags, image, git commit).

How it differs from the current pipeline

Current pipelineThis template
Structure One monolithic pipeline/__main__.py — all steps in one run One module per step in pipeline/; any step runs alone
Cluster jobs One job for the whole chain — rerun everything to redo one step One job script per step (scripts/*.py) + whole-chain script; DNS-1123 job names
Dataset registration Hardcoded demo layout — class subfolders, *.csv only Your real data: cohort table (csv/xlsx), regex, or folder scan (any file type)
Dataset config CLI flags per run, demo-only experiment One experiment YAML per dataset, versioned in git; EXPERIMENT constant for the jobs
Provenance Unchanged — still every step an MLflow run: user → dataset (sizes/mtimes) → verify → inputs → outputs. Now per-step instead of per-whole-run.

What to look for in the MLflow UI

Dataset_Registry experiment

  • A run per dataset version, file_sizes / file_mtimes tags — the fingerprint that verify_dataset checks your disk against.

Your experiment (e.g. "Dataset Mammaprint")

  • One run per step, tagged step=...
  • dataset_verified, git commit, docker image, hardware, seeds, job_* (cluster, CPU/memory) when run as a kube-job
  • Params: the whole resolved Hydra config
  • Artifacts: train.csv/test.csv, embeddings/, cluster/, frozen requirements, console.log
  • embed_dataset/learn list their upstream under input_uris — the chain is traceable end to end

Notes for real (WSI) data

  • Registration & split work on any file type (e.g. .mrxs).
  • embed_dataset/learn expect per-sample feature files — insert your own WSI featurization step there.
