🔗 Runs find each other

Downstream steps use the latest finished upstream run, or a pinned runs:/… URI in the experiment config — the chain stays traceable (input_uris).

📍 Data stays in place

Files stay where they are on the cluster — nothing is copied or created. Only manifest.csv is written into data_path.

What you must do — setup (once)

terminal
# create the environment
$ uv sync

# point at your MLflow server + identify yourself
$ export MLFLOW_TRACKING_URI=...
$ export MLFLOW_USER=...
terminal
# register yourself — once, ever
# username is automatic (kube config / JOB_USER);
# other identity: configs/pipeline/create_user.yaml
$ uv run python -m pipeline \
      pipeline=create_user +experiment=mammaprint

One run in User_Registry — links all your future runs to you. The username is the one kube-jobs uses (JOB_USER), so cluster runs link automatically.

What you must do — one YAML per dataset

configs/experiment/mammaprint.yaml
metadata:
  experiment_name: Dataset Mammaprint
  description: dataset init

data_path: /mnt/data/MOU/breast/mammaprint

pipeline:
  source:  null          # or cohort.xlsx
  pattern: '.*\.mrxs$'    # or null
  path_column: null      # table mode only
  label_column: null      # table mode only

dataset:
  name: mammaprint
  version: 1.0.0
  mlflow_uris:            # pin = freeze chain
    split_dataset: null
    embed_dataset: null

Run the steps

💻 Locally, in order

terminal
$ uv run python -m pipeline pipeline=register_dataset +experiment=mammaprint
$ uv run python -m pipeline pipeline=split_dataset     +experiment=mammaprint
$ uv run python -m pipeline pipeline=embed_dataset     +experiment=mammaprint
$ uv run python -m pipeline pipeline=learn             +experiment=mammaprint

Each run prints the provenance chain and a [hint] line showing how to pin it for downstream steps.

☁️ On the cluster — one job per step NEW

terminal
# once: uv sync --extra job · edit scripts/_submit.py (image, EXPERIMENT)
$ uv run python scripts/register_dataset.py   → provenance-register-dataset
$ uv run python scripts/split_dataset.py       → provenance-split-dataset
$ uv run python scripts/embed_dataset.py       → provenance-embed-dataset
$ uv run python scripts/learn.py               → provenance-learn

# or the whole chain in one job:
$ uv run python scripts/submit_pipeline.py

Username comes from your kube config; jobs record job_* tags (cluster, CPU/memory, image).

How it differs from machine-learning (mlkit only)

🧪 RationAI/machine-learning

Lightning + Hydra + MLflow + uv — the quickstart this template builds on
ml/ data modulemode=fit / validate / test / predictpreprocessing/ qc · tiling · masks
📊 mlkit MLFlowLogger — params, metrics, artifacts
❌ runs are isolated: who ran it is just an MLflow username,
which files it saw is a path in the config, no upstream links,
nothing checks the data on disk

🧬 prov-ml-template — mlkit + provenance

same skeleton — Hydra configs · MLflow via mlkit · experiment YAMLs · kube-jobs
👤 User_Registry — who ran it (username from the kube config)
🗂️ Dataset_Registry — which files: sizes/mtimes fingerprint,
✂️ split verifies the disk against it before training
🔗 runs chained via input_uris — which run produced what
🛰️ env captured: git commit · image · hardware · job_* tags

Result: a W3C PROV document can be assembled from the runs — who ran what, on which data, with which code and environment. Provenance is layered on top of the mlkit backbone, not a rewrite.

🩹 Real (WSI) data — two notes

• Registration & split work on any file type (.mrxs, .svs…).

• embed_dataset/learn expect per-sample feature files — insert your own WSI featurization step there.
