PART 1 · KUBE-JOBSevery step is a cluster job

One script per step → one job per step

terminal
# once: uv sync --extra job · fill the TODOs in scripts/_submit.py
$ uv run python scripts/split_dataset.py  → job provenance-split-dataset
$ uv run python scripts/embed_dataset.py  → job provenance-embed-dataset
$ uv run python scripts/learn.py          → job provenance-learn

# switch dataset — one line, nothing else:
EXPERIMENT = "mammaprint"   # scripts/_submit.py

🔤 DNS-1123 job names

k8s names allow no underscores — jobs are provenance-<step> with hyphens; the pipeline step itself keeps its name.

🔁 Rerunnable by default

The previous job is auto-deleted before submitting (submit_job rejects existing names) — rerun a step as often as you like.

📦 Inside every job: git clone + checkout → UV_FROZEN=1 + uv sync (never refresh the kube-jobs source in-cluster) → run the step · storage mounts for DATA and PROJECTS · CPU/memory from the script.

PART 1 · KUBE-JOBSidentity, hardware tags, the chain

The job is you — and the whole chain is one job

👤 Username from your kube config

It becomes JOB_USER inside the job — the exact name provenance looks runs up by. Cluster runs link to you with zero configuration (only MLFLOW_TRACKING_URI comes from the cluster).

🏷️ Hardware & cluster recorded

Jobs get job_* tags — cluster, CPU/memory, image — from kube-jobs env vars, plus console.log (stdout capture).

terminal
# or the whole chain in one job:
$ uv run python scripts/submit_pipeline.py

🔗 The chain forwards its own pins

Each step tees to job.log; the next command gets $(grep '^\s+dataset\.' job.log) — the printed [hint] pins are passed on automatically, under set -eo pipefail. A fresh chain runs end-to-end with nothing pasted.

PART 2 · PROVENANCEhow it works

Three registries answer three questions

👤 User_Registry — who

One run per person (create_user, once ever). Your kube username is the key — every run you start is linked to you.

🗂️ Dataset_Registry — what data

One run per dataset version (Adam's register_dataset): the fingerprint — file sizes + mtimes — that later steps verify your disk against.

▶ pipeline runs — what happened

One MLflow run per step: user, git commit, docker image, hardware, seeds, upstream inputs, output artifacts — chained by pinned URIs.

inside every step — the whole provenance change
log_provenance(config=config)   # user · dataset fingerprint
                                # git commit · image · hardware
                                # seeds · upstream inputs

🏛️ From these runs, a W3C PROV document can be assembled — who ran what, on which data, with which code and environment.

PART 2 · PROVENANCEthe three rules

What makes it trustworthy

🔎 The disk is verified

split_dataset re-walks the folder and checks every file against the registration fingerprint → tags the run dataset_verified. Changed files since registration? You see it, not silently analyse it.

📌 Nothing resolves implicitly

A step consumes exactly the run pinned in its config — never "the latest". A missing pin fails immediately and prints the [hint] line to paste. Old runs stay reproducible.

📍 Data is used in place

Files stay where they are — nothing is copied or moved. Only manifest.csv is written into the folder; splits are lists of files, logged as small CSV artifacts.

▶ what one run records

tagsstep · dataset_verified · git commit · docker image · hardware · seeds · job_* paramsthe whole resolved Hydra config (cfg_*) artifactstrain/test.csv · embeddings/ · cluster/ · frozen requirements · console.log inputsinput_uris → the upstream run it consumed

🧪 Verification failure aborts? In the pipeline steps it tags dataset_verified=False and continues; in mlkit training (ProvenanceCallback) set fail_fast: true to abort.

PART 3 · YOUR WORKFLOWprerequisite — Adam

ADAM  PREREQUISITE Register the dataset — once per version

Expected of Adam, needed by everyone — no analysis can run before it.

Data is on the cluster — any file type (.mrxs, .svs…), any folder shape.
Copy an experiment YAML and fill in the three data things: 
data_path: /mnt/data/.../mammaprint
pipeline:
  pattern: '.*\.mrxs$'   # how to find the samples
dataset:
  name: mammaprint        # + version
Run one command — manifest is built, fingerprint stored: 
$ uv run python -m pipeline pipeline=register_dataset \
        +experiment=mammaprint
[hint] ... dataset.run_id=f94f159b…
Hand it over — commit the YAML to git, send the user the run_id.

What it needs → what it produces

needs: the data on the cluster + 3 YAML entries — data_path, pattern/source, name+version

produces: manifest.csv · a Dataset_Registry run with the dataset fingerprint (file sizes + mtimes) · the run_id he sends you

Three ways to point at the samples

📊 Cohort table — the csv/xlsx that ships with the data:
source: cohort.xlsx + path_column / label_column

🔎 Regex — folder + “what to find”: pattern: '.*\.mrxs$'
label = named group (?P<label>…) or parent folder · recursive

🌳 Folders — one subfolder per class, any file type

   verifies the disk · runs don't know their upstream

@autolog
def main(config, logger: MLFlowLogger):
    mlflow.set_tag("step", config.pipeline.step)
